# First metal experiment — Dynamixel XL330

Physical-evidence milestone. Not a kernel redesign. Not certified safety.

## Chosen actuator

| Item | Value |
|------|--------|
| Actuator | Robotis Dynamixel **XL330-M288-T** (also accept XL330-M077-T) |
| Controller | Servo onboard MCU + USB–UART adapter (U2D2 / FTDI / CP2102) |
| Supply | **5.0 V**, current limited to **≤ 0.5 A** at the bench PSU |
| Interface | Dynamixel Protocol 2.0, default **57 600** 8N1 on `/dev/ttyUSB*` (probe also tries 115 200, 1 Mbps, and Wizard **9 600**; **2 / 3 / 4 Mbps** only when `REALITYOS_METAL_BAUD` or `metal.json` already names that rate) |
| Max configured velocity | Profile Velocity **20** (≈ 4.6 rpm) |
| Max configured effort | Position-mode **PWM Limit(36)** cap `max_pwm_limit_raw` default **200** (~22.6%; raw × 0.113 ≈ percent of full PWM; 885 ≈ 100%). This is an **output/PWM cap**, not a certified torque limit. Current Limit **200 mA** may still be written; it is **not** the Position Mode torque boundary. Reality OS `tau_max` **0.2** |
| Operating mode | Driver sets EEPROM **position control (3)** if it is not already |
| Mechanical constraint | Horn fixture or zip-tie stop that still allows the certified **32-tick** (~2.8°) step; **no load**, no linkage, no person in the sweep |

Why this is low-energy: stall torque is about **0.52 N·m** at 5 V, plastic gears, no mobile base, no high-voltage bus. Unexpected motion cannot throw a mass or travel.

Do **not** start with a humanoid, industrial arm, high-torque BLDC, or anything that can travel or crush.

## Independent physical power cutoff

The servo **VIN** (not the USB data path) must pass through an operator-accessible disconnect:

* appropriately rated **bench PSU output switch**, or
* **SPST / in-line barrel disconnect** rated **≥ 2 A** on the 5 V rail.

Reality OS torque-disable is a register write. It is **not** the cutoff.

This cutoff is **not** STO, SS1, PL, or SIL unless the chosen hardware’s own documentation says it is and that certification is in force. A bench switch is none of those.

Operator test: open the switch; the servo must lose holding torque while USB/data may stay enumerated. Record `REALITYOS_METAL_CUTOFF_TESTED=1` only after that observation — that flag is **operator attestation** (`cutoff_operator_attested`) and **cannot** mint `measured_success` by itself. Live campaign measurement `REALITYOS_METAL_CUTOFF_LIVE=1` waits for VIN/comms to drop independently of a Reality OS torque-disable command and sets `cutoff_live_observed`. Only `cutoff_live_observed = true` satisfies the metal success gate.

## Identity mapping

`probe_identity()` reports:

| Field | Source |
|-------|--------|
| `serial` | **Measured:** USB adapter serial (sysfs) + servo bus ID, else USB vid:pid:bus:devpath, else tty name + rdev (UART/GPIO). XL330 EEPROM has **no** factory serial. |
| `firmware_id` | **Measured:** model number register 0 + firmware version register 6 (`xl330-m288:1200:<fw>` on the chosen M288; M077 is `xl330-m077:1190:<fw>`). |
| `actuator_ids` | **Measured:** `xl330:<id>`. |
| `calibration_id` | **Deployment:** `metal.json`, not EEPROM. |
| `design_content_hash` | **Deployment:** SHA-256 of `realityos.metal_design/1` (limits). Not EEPROM. |

If USB serial cannot be read, a `usb:<vid>:<pid>:<bus>:<devpath>` fallback is used if sysfs exposes both busnum and dest. If that is also missing, the char-device name and `rdev` are used (`tty:<name>:<rdev>:id<n>`). That is measured from the OS node, not invented EEPROM. Values are not invented. `/dev/serial/by-id/*` paths are canonicalized to the real tty name before the sysfs walk. The campaign and `serve` refuse `/dev/pts/*` unless `REALITYOS_METAL_PTY_SEQUENCE=1` **and** the node is a PTY (`scripts/metal-pty-sequence.sh`). That dry-run exercises the real campaign script; it must finish with `experiment_status != measured_success`, `cutoff_live_observed=false`, and must **not** install `docs/metal_proof.json`. Setting the flag on a real `ttyUSB*` / `ttyACM*` is ignored.

Model and firmware are latched at identify time. The motion-block sensor packet does not contain those EEPROM fields and does not invent them. On live I/O each sensor also re-reads model/firmware/id (addr 0, 8 bytes) **only when that motion read finished in <15 ms**, so a physical servo swap on the same USB-UART updates `probe_identity` before write-time `verify_live_hardware`. An identity CRC/NAK after a good motion sample does **not** latch `bus_lost` or drop the motion row; a later model/firmware mismatch still fail-closes at write-time verify. XL330 EEPROM has **no useful factory unique actuator serial**. An identical-model, identical-firmware servo swapped behind the same USB adapter and bus ID may be indistinguishable. This experiment binds USB adapter identity + bus ID + model + firmware + deployment calibration/design. That is **not** a claim that arbitrary production robots always provide unique hardware identity. Campaign `hot_swap.json` still overlays identity without changing EEPROM.

## Composition

`realityos-metal-smoke serve` calls `RuntimeSession::start_online` → `OsMonotonicClock`. It does not use the HIL `Authority` object or `FakeClock`. `new_online` heartbeats (durable start transition), then `watchdog_tick_now` stamps the software watchdog **in memory**. Successful normal pets do **not** `fsync` journal+seal and do **not** move the stamp after durable work. Miss/ESTOP and other major transitions remain fail-closed and durably recorded. A real gap longer than the configured interval is still visible when execution resumes. This software supervisor is **not** an independent hardware watchdog. Idle serve pets about every 40 ms (in-memory) and heartbeats about every 800 ms (heartbeat still fsyncs journal+seal). The idle loop accepts a waiting IPC client *before* the idle heartbeat; a heartbeat persist in the same iteration as `handle` can consume the 100 ms window (refuse at the first handle pet, empty `serve.err`). Serve does **not** restamp the watchdog after heartbeat persist. Serve does not pet again on accept — `handle` pets. After `handle`, the idle Instant is pushed out so status-then-propose does not add another idle heartbeat. Propose ticks the watchdog once on IPC accept; it does not heartbeat between sensor acquire and the certified write (`dispatch_issued` ticks immediately before `write_online`). After the write, serve does **not** restamp the watchdog to hide prepare/consume/emit fsync time. After identify, live I/O is one attempt with a **40 ms overall deadline** (dribbled 4×40 ms reads are 160 ms and miss the watchdog). Sensor sampling is a single 26-byte RAM block. Propose pets the watchdog again after acquire so dispatch does not inherit that read. Setup enables torque after the EEPROM settle so the first certified write is only `goal_position` (not torque-on + goal). Goal writes reuse the last sensor present and skip redundant profile/torque pokes. `scripts/metal-kill-serve.sh` kills leftover `serve` processes for a metal root so a zombie cannot rewrite journal+seal after `rm -rf` and poison `--first-online`.

Keep `REALITYOS_METAL_ROOT` on tmpfs. The campaign default is `/tmp/realityos-metal`; if that path is not already tmpfs, `scripts/metal-campaign.sh` mounts a 32 MiB tmpfs there (override with `REALITYOS_METAL_ALLOW_SLOW_DISK=1` only to debug, knowing a journal fsync >100 ms can still miss the software watchdog on a durable transition). Successful watchdog pets are cheap. Heartbeat and ESTOP still fsync. That is a deployment constraint, not a certified hardware watchdog.

Users: `realityos-authority` owns the tty, key, journal, and process. `realityos-autonomy` may use only the Unix socket. The metal root is `0751` so autonomy can traverse to `ipc.sock` (`0660` / `realityos-ipc`); `bus/` stays `0700`. A `0750` root would make IPC and `direct_device_open_attempts` fail closed without measuring the attacks. After each `serve` bind the campaign re-applies `0600` on the tty because udev may restore `0660 dialout`. On `ttyUSB*` / `ttyACM*` it also installs a temporary udev rule (`ID_MM_DEVICE_IGNORE`, `ID_BRLTTY=0`, owner/mode). If `fuser` still shows brltty or ModemManager on that node, the campaign stops those services for the run (and starts them again on exit). Any other holder still fails closed. `os-probe` measures `/proc/<pid>/fd` against the `realityos-metal-smoke` child, not the `sudo -u` wrapper.

Identity/disconnect ESTOP is not a software-watchdog miss. `serve` pets the watchdog on tick success only, so recover-after-identity can return `hardware_session_requires_online_restart` instead of a vacuous `software_watchdog_miss`. Campaign `force_disconnect` is an identity overlay (USB may stay enumerated) so propose reaches `verify_live_hardware` and FAULT/ABORTs the instance; clearing the hook cannot revive it. Live I/O loss (VIN drop, USB-UART timeout) is detected on acquire, before write-time verify; the metal serve latches `bus_lost` and recover cannot resurrect that instance (missing-sensor campaign hook is not a bus loss). Authorized hold/nudge must produce exactly one certified serial TX (`write_all`+`flush`), a successful Status Packet, and a later authority-owned present sample. Hostile cases must include the expected violation token, must not be a watchdog miss, and must have `serial_tx_delta = 0`, `physical_writes_delta = 0`, and `unauthorized_device_ack_delta = 0`. A dead session before those cases fails the campaign instead of minting `docs/metal_proof.json`. `measured_success` is not `write_delta >= 2`. It requires the PWM cap configured and read back, the absolute startup cage active, TX+ACK+post-sensor hold and nudge, zero unauthorized certified TX/ACK, live independent VIN cutoff observed, the post-TX/pre-status crash restart with zero retransmission, and the other listed gates. PTY stand-in cannot mark success.

## Sensor freshness

* Device capture: XL330 Realtime Tick (wrapping 1 ms counter) as `timestamp_s`.
* Freshness: authority monotonic receive time stamped by `ingest_sensor_packet`.
* Threshold: `freshness_threshold_s` in `metal.json` (default 2 s), recorded into the proof from `bus/sensor_freshness.json`.
* Autonomy cannot ingest or refresh evidence (`sensor_samples` is refused).
* Observed motion is measured from `bus/present` / `bus/goal` (device registers), not inferred from IPC status. `bus/present` is the last acquired sample (pre-write during propose). After an authorized hold/nudge the campaign waits until present is inside the hold-still band of the written goal **and** Moving is not 1, then re-acquires so `valid_nudge` records a present change; a goal write against a stale cache is not motion. A real XL330 leaves Moving=0 while accel is still below Moving Threshold (addr 24) — that is “not yet traveling”, not arrived. A first Moving=0 sample would record nudge delta=0. A fixed 300 ms sleep can also sample while the profile (velocity 20 + accel 10 ≈ 230 ms for 32 ticks) is still traveling. The certified nudge is `action=0.2` (the full 32-tick / ~2.8° cap) so plastic-gear backlash is less likely to hide the step.
* Hold-still acceptance is **|present delta| ≤ 4 ticks** (~0.35°). XL330 quantization is 0.088°/tick; no-load Position P Gain 400 hunt is not specified as 0. A hold that travels the 32-tick step fails. A nudge whose present change stays inside that hunt band fails (1–2 count flicker is not item 8). This band is experiment acceptance, not certified positioning accuracy.

## Proof

`docs/metal_proof.json` schema `realityos.metal_proof/1` is written only from measured cases on a real device. `measured_success` requires supported non-PTY XL330 measured; EEPROM model match; `OsMonotonicClock` and `HardwareDriverPort`; conservative PWM cap configured and read back; absolute position cage active; `valid_hold` with exactly one certified serial TX, successful ACK, later present inside the hold-hunt band and the cage; `valid_nudge` with exactly one certified serial TX, successful ACK, later present that moved farther than hunt **toward** the commanded goal, with present and goal inside the cage; zero unauthorized certified serial TX / `physical_writes_delta` (copies of `serial_tx_*`) and zero unauthorized successful device ACK; direct-device OS attempts > 0 and successes = 0; identity-change and disconnect refusals measured; `after_serial_tx_before_status` restart `serial_tx_delta = 0`; all other ambiguous crash restarts `serial_tx_delta = 0`; sensor device-capture and authority-receive evidence; **live** USB-UART unplug observed (`unplug_live_observed`; `force_disconnect` / `hot_swap.json` are campaign hooks); **live** independent VIN cutoff observed (`cutoff_live_observed`, not merely `REALITYOS_METAL_CUTOFF_TESTED` / `cutoff_operator_attested`). A write attempt is not a physical device write. An ACK without post-command present is not enough. Motion is not inferred from Goal Position. PTY stand-in identity (`PTY_STAND_IN_NOT_METAL` / `metal=false`) cannot mark success. `hardware_model` is taken from the probed model number (1200 → XL330-M288-T, 1190 → XL330-M077-T; Robotis e-Manual / Dynamixel2Arduino); a missing, unknown, or swapped model refuses the proof meta. The campaign reporter writes the artifact and a 16-point `METAL_PROOF_REPORT.md` into the metal root (authority-owned). Root installs both into `docs/` only when `experiment_status` is `measured_success`. CI and the PTY sequence must **not** create `docs/metal_proof.json`. The authority UID does not need write access to the repository. The reporter refuses to emit a success artifact when `hardware_present` is false. It does not overwrite `docs/hil_proof.json`. The PTY Protocol 2.0 stand-in in `crates/metal/tests/` is a driver regression test, not physical evidence. Its `HardwareIdentity.metal` is false and `evidence_status` is `PTY_STAND_IN_NOT_METAL`. `scripts/metal-os-boundary.sh` measures the two-UID filesystem/device-open boundary only; it is not physical evidence and must not write `metal_proof.json`. Serial open uses serialport exclusive mode (TIOCEXCL + flock on the tty) plus an authority-owned sidecar lock.

Certified-command evidence counters (not setup/sensor traffic): `command_egress_attempts` (`record_attempt` — intent only), `serial_tx_completed` (after the entire command frame passed `write_all`+`flush`), `device_acknowledgements` (successful Status Packet). Every CaseRecord records those deltas plus `physical_writes_before` / `after` / `delta` (copies of `serial_tx_*`, the named objective-8 egress counters — not `bus/writes` attempts) and observed post-command present. Session cage `max_total_excursion_ticks` (default 48) is derived from startup Present Position, clamped to the XL330 Position Mode legal window, written to EEPROM Min/Max Position Limit with torque off, read back, left fail-safe after crash, and restored on orderly teardown. Per-command delta is not enough: 100 valid positive nudges must not escape the cage. If the conservative PWM cap cannot move an unloaded horn, the experiment is incomplete until an operator raises `max_pwm_limit_raw`. Software must never silently restore factory PWM Limit 885 to make a test pass.

## How to run (bench host)

```text
# 1) Operator-test the VIN cutoff first (servo loses holding torque).
# 2) Close the cutoff again.
# 3) Build, then run. CUTOFF_TESTED is operator attestation only.
#    measured_success also requires a live USB-UART unplug (when prompted)
#    and a live VIN drop (open the same disconnect when prompted).
cargo build -p realityos-metal --bins
sudo -E env REALITYOS_METAL_DEVICE=/dev/ttyUSB0 \
  REALITYOS_METAL_BIN=$PWD/target/debug \
  REALITYOS_METAL_CUTOFF_TESTED=1 \
  REALITYOS_METAL_CUTOFF_LIVE=1 \
  REALITYOS_METAL_UNPLUG_LIVE=1 \
  scripts/metal-campaign.sh
```

The campaign creates system users `realityos-authority` / `realityos-autonomy` and group `realityos-ipc` if they are missing (same accounts as HIL CI), **before** the first USB prepare so udev `OWNER=` can resolve. It also refuses to open the UART if `python3`, `timeout(1)`, or (on a real USB-serial) `fuser` / `udevadm` is missing. First prepare runs before the journal tmpfs and binary staging; `metal-deploy` `chown` on the tty can emit a udev `change` that wakes ModemManager and resets FTDI `latency_timer`. The campaign prepares again immediately before `probe` opens the UART, skips a no-op tty `chown` / `latency_timer` / `power/control` write, and settles/rematches after a real claim or sysfs write so probe does not open during that change. After that settle it fails closed unless `latency_timer` (when present) still reads `1` and UART `power/control` still reads `on`. After each `serve` bind it re-asserts owner/latency/power, settles, and fails closed unless those values still stick — those post-open writes used to sit inside `if` without `|| return`, so a failed `latency_timer` write was ignored (`set -e` is disabled in `if`) and the first hold could run at 16 ms. The driver skips a no-op `chmod 0600` on open (same udev `change` class). Probe broadcast sniff takes exclusive on a real UART. A bench that never ran `hil-os-users-ci.sh` used to exit 2 in `metal-deploy` before probe, or install a udev rule for a user that did not exist yet. Without `fuser` the campaign used to skip the holder check and open a UART ModemManager already had. Writing `ID_MM_DEVICE_IGNORE` then `udevadm control --reload || true` used to announce success without loading the rule; a leftover `99-realityos-metal-*.rules` from a SIGKILL'd run used to skip rewrite; `fuser` ran only before `udevadm trigger --action=change`, which can wake ModemManager. Reload must succeed, `udevadm info` must read `ID_MM_DEVICE_IGNORE=1` on the live tty, and the holder check runs again after that trigger. That trigger can re-enumerate FTDI/U2D2 as `ttyUSB1`; the campaign rematches the recorded USB identity and rewrites `metal.json` *after* the trigger, not before.

Do **not** copy `REALITYOS_METAL_BAUD=1000000` into that command. 1 Mbps is already in the automatic scan, after factory 57 600. Set `REALITYOS_METAL_BAUD` only when the XL330 is already at a Wizard **2 / 3 / 4 Mbps** rate (those are not scanned unless named). Probe still tries factory 57 600 first even then, so a mistaken high-rate hint cannot wedge a CH340 before the factory servo is found.

The campaign exits 2 before `init`/`probe` (which enable torque) unless `REALITYOS_METAL_CUTOFF_TESTED=1`. That flag is operator attestation, not live cutoff evidence and not a certified STO/SS1 function.

`REALITYOS_METAL_BAUD` and `REALITYOS_METAL_SERVO_ID` are optional **probe hints**. Probe always tries factory **57 600** first (and retries it immediately — U2D2/FTDI often drop a cold first packet), then 115 200, 1 Mbps, and Wizard **9 600** last. 2 Mbps / 3 Mbps / 4 Mbps join that scan only when the probe hint or `metal.json` already names them, and only **after** those factory/common rates — a CH340/CP2102 (datasheet max ~2 Mbps) can wedge after a high-rate open, so a 1 Mbps docs hint or a mistaken 2/3/4 Mbps Wizard hint that led the scan used to miss a factory 57 600 servo. The first scan rate (factory 57 600) is retried immediately, before any other rate. 1 Mbps still joins every scan after 115 200; factory 57 600 is retried immediately before that open, and before each leftover 2/3/4 Mbps open, so a DTR-RESET miss during the first factory/115 200 windows does not walk into a CH340-wedge rate next. `serve` rematches the USB-UART **device** from env (udev rename) but must not apply the baud/id hint: the documented example `REALITYOS_METAL_BAUD=1000000` on a factory 57 600 XL330 used to make crash-replay talk 1 Mbps and die before hold. The campaign exports the discovered pair after `bind-measured`. At each baud it broadcast-PINGs (id 254) so a Wizard ID other than 1 or 2 is found before the candidate list. It waits 100 ms after open before the first ping (U2D2/FTDI often drop a cold first packet), waits 100 ms after a failed pair, retries the configured pair once after the scan, and writes the working pair into `metal.json`. Serial open does **not** assert DTR/RTS from userspace: on many FTDI/CP2102 adapters DTR is servo RESET. Linux still asserts DTR on the first open; the driver takes exclusive, then clears HUPCL on that fd via termios (`cfmakeraw` keeps kernel-default HUPCL; `stty -F` after `TIOCEXCL` is EBUSY on the node and on `/proc/<pid>/fd/N`) so probe close / crash-replay does not DTR-RESET. Discover holds that exclusive fd and retunes baud in place so each 115 200 / 1 Mbps / hinted 2/3/4 Mbps attempt is not another DTR-RESET. Real UART settles 500 ms after the first open (Robotis reboot window plus cheap FTDI/CP2102 DTR-RESET); PTY stays at 100 ms. A udev rematch to a new node still reopens once. After each host TX a real UART waits 1.5 ms so a cheap TTL/RS485 DE/RE can release the line (U2D2 does this internally; do not toggle RTS). U2D2 does not wire DTR to RESET. After the first PING, setup writes Status Return Level **2** without requiring an ack. Wizard can leave that register at **0** (PING only); READ/WRITE then have no status packet and identify would miss. The campaign writes the udev ignore rule for the locked USB identity (overwriting a leftover file), fails closed unless `udevadm control --reload` succeeds and `udevadm info` reads `ID_MM_DEVICE_IGNORE=1`, and triggers `change` only when that property is missing — re-triggering every crash-replay can reset `latency_timer` to 16 ms. That trigger can re-enumerate FTDI/U2D2 as `ttyUSB1`; the campaign rematches the recorded USB identity and rewrites `metal.json` after the trigger, then checks holders again. Each campaign kills leftover `realityos-metal-smoke --root <root>` processes, wipes `REALITYOS_METAL_ROOT`, and mounts tmpfs on that path when the parent filesystem is a disk so `--first-online` is not refused by a leftover journal and idle journal fsyncs stay inside 100 ms. Crash-replay waits at most 5 s for the smoke child to exit; if `crash_if` never fires the campaign fails instead of hanging on `wait`. Set `REALITYOS_METAL_CUTOFF_TESTED=1` only after opening VIN and seeing lost holding torque; the campaign will not torque or write without it. On `ttyUSB*` / `ttyACM*` / `ttyCH341*` the campaign sets the USB-serial `latency_timer` to 1 ms when sysfs exposes it and fails closed if that file exists but the value does not stick (FTDI/U2D2 default 16 ms can miss the 40 ms live I/O deadline). CH340/ch341 often has no `latency_timer` file; that is skipped., writes a temporary udev rule so ModemManager and brltty ignore that tty, stops brltty/ModemManager if they already hold the node, and exits 2 if another process still has it open. That check runs before every `serve` start (probe→serve, disconnect restart, crash-replay) and waits briefly for our own close so a leftover smoke fd is not mistaken for ModemManager. The PTY campaign sequence skips that exclusive-tty fail: the stand-in must hold the PTY master, and `fuser` would otherwise treat `python3` as a foreign holder and exit 2 (CI `os-users`). Protocol 2.0 `STATUS_ALERT` (bit 7) is leftover Hardware Error Status, not an instruction NAK; setup reboots the servo once if that latch is set, then refuses if the error remains (VIN still out of range). Status Return Level is forced to 2 after PING so a Wizard-set 0 does not strip status from READ/WRITE.

`scripts/metal-os-boundary.sh` (CI `os-users`) proves the 0751 / device-open counting path with a dummy 0600 file, then a two-UID `serve` + hold on the PTY Protocol 2.0 stand-in (`REALITYOS_METAL_ALLOW_PTY=1`). The IPC journal root is tmpfs (`/dev/shm` or a 32M mount); a GHA `/tmp` disk fsync >100 ms latched `software_watchdog_miss` on the first hold. That is **not** a substitute for the XL330 campaign and does not write `metal_proof.json`. `scripts/metal-pty-sequence.sh` runs the full campaign script against the same PTY responder (also CI `os-users`); it is a first-contact dry-run of restart/crash-replay, not metal evidence. It must finish with `experiment_status != measured_success` and must not install `docs/metal_proof.json`.

First-contact script invariants (found on the PTY sequence, would fail the first XL330 run):

* GNU `stat -c '%a'` prints `600` for mode `0600`. Comparing the raw string to `0600` failed after a correct `chmod` and aborted every real USB-UART owner claim (`usb_tty_owner_mode_ok` / `metal-deploy`). Compare octal values (`scripts/metal-unix-mode.sh`).
* `before_prepare` never reaches durable prepare. Restart must not auto-retransmit. Replaying that command ID after restart is a new journal command, not a duplicate of a hardware write. Measure serial TX across crash+restart only; do not treat a later same-ID propose as the ambiguous-execution retry invariant.

* Empty `METAL_CMD_ID` must not override `--id`. Autonomy used to export the empty string; propose treated `is_ok()` as a set id, minted `metal-{now}`, and made the `metal-hold` replay look like a new write.
* Planned `stop_auth` writes `$ROOT/stop_serve` so Drop torque-offs and releases the tty. SIGKILL skips Drop; a real XL330 would keep torque and the next open can get `EBUSY`.
* PTY `TIOCEXCL` survives `process::exit` (`crash_if`). Serial open uses `exclusive(false)` only on `/dev/pts/*`; real tty keeps exclusive. The sidecar flock still serializes.
* Crash-replay must not `wait $AUTH_PID` unless the smoke child actually exited. `after_write_before_ack` / `after_ack` fire only after `act()` returns Ok; a refused propose leaves serve up. `during_write` is **before** transport (after the egress attempt). `after_serial_tx_before_status` is the true ambiguous transport crash: after command `write_all`+`flush`, before the Status Packet. The restarted process must not retransmit that command (`serial_tx_delta = 0`). Propose IPC has a 20 s I/O timeout so a wedged serve cannot hang the campaign. After `crash_if`, `fuser` on a USB-UART can still show a holder; `start_auth` retries that instead of `exit 2` (which skipped the open retry and would abort the first XL330 crash-replay). The crash serve, the post-crash restart, and the reset-hold restart must also wait for a live `ok=true` sensor — `crash_if` is a new USB-serial open and cheap FTDI/CP2102 DTR-RESET the horn; a bound `ipc.sock` with `ok=false` used to abort the first reset hold.
* Journal continuity treats `replayed` as an identity marker (`repeated_refuse_n` defaults to 3). The campaign `metal-hold` replay plus two crash-replays latch the next `--restart` as `abort_latched:replayed`, so `after_write_before_ack` never reaches `crash_if`. After each measured crash-replay the campaign does one authorized reset hold (not a proof case) so the next crash point is a live instance.
* Wizard Status Return Level `0` answers PING only. Identify READs then miss. After the first PING, setup writes `2` and consumes an optional status (factory `2` replies; Wizard `0` does not) so a late USB packet is not decoded as the model number.
* Wizard min/max position limits NAK a goal outside that window. Setup reads the EEPROM window, then establishes a session absolute cage around startup Present (`max_total_excursion_ticks`, default 48, clamped to legal 0–4095 and the Wizard window). It writes those EEPROM Min/Max limits with torque off, verifies readback, leaves them fail-safe after crash, and restores the previous values on orderly teardown. Driver-level command enforcement refuses a goal or present outside the cage. It does not auto-step inward and does not widen limits against a fixture.
* Wizard PWM/velocity/current mode is EEPROM. After forcing position mode (3), setup waits and re-identifies before RAM profile/torque writes.
* `valid_nudge` must change device present, not only increment the egress write count. Propose persists the pre-write present; the campaign re-samples after a short settle.
* Wizard baud 2 Mbps / 3 Mbps / 4 Mbps is a hint (`REALITYOS_METAL_BAUD`), not an automatic scan, and is never opened before factory 57 600 / 115 200 / 1 Mbps. A CH340/CP2102 can wedge after those opens; a 1 Mbps docs hint or a mistaken high-rate hint that led the scan then never recovered the factory servo. Factory 57 600 is retried immediately after the first miss, before any other rate. Non-1/2 servo IDs are still found by broadcast PING.
* Wizard EEPROM Velocity Limit `0`/`1` caps motion so a 32-tick nudge is still sitting at the old present when Moving clears. Setup raises that limit to at least `max_profile_velocity` (does not raise a higher factory cap). Time-based Drive Mode is forced to velocity-based so profile velocity stays in rpm, not milliseconds.
* A parked XL330 hunts a few present counts. Requiring hold present delta == 0 fails a correct no-load hold. Proof and campaign accept |delta| ≤ 4 ticks for hold and require |delta| > 4 for nudge.
* After an authorized write the campaign waits until present is inside the hold-still band of the written goal and Moving is not 1 (1.5 s cap). A first Moving=0 is “not yet traveling” on a real XL330 (accel below Moving Threshold). Sensor persists Moving as `bus/moving`. Setup lowers Wizard Moving Threshold when it is above profile velocity (factory 10). The PTY campaign sequence delays present and keeps early Moving=0 so this path is exercised.
* Live sensor re-reads model/firmware/id (addr 0, 8 bytes) only when that motion read finished in <15 ms. A physical XL330 swap on the same USB-UART used to keep the latched firmware, so `verify_live_hardware` would still match. The motion block does not carry those fields. Identical model+fw units still cannot be distinguished. Identity CRC/NAK after a good motion sample does not latch `bus_lost` or drop the row; a complete bad-CRC status fails immediately instead of burning the 40 ms live deadline.
* Half-duplex turnaround: after `flush()`, a real UART sleeps 1.5 ms before the first read so a cheap TTL/RS485 DE/RE can release the line (broadcast sniff, SRL poke, and ID-register reads included). A PTY skips the sleep. U2D2 handles turnaround internally. Do not toggle RTS (DTR-RESET risk).
* Wizard Protocol Type (addr 13) 20/21/22 is S.BUS / iBUS / RC-PWM. RC-detected boot auto torque-ons and stops speaking Protocol 2.0. If the bus is already in the no-RC Protocol 2.0 fallback, setup writes **2**. A servo that is already in RC mode cannot be identified.
* Wizard Feedforward 1st/2nd (addr 90/88) makes a 32-tick goal overshoot. Setup writes 0 when either is non-zero. Factory is 0.
* Wizard Position I Gain (82) / D Gain (80) do the same. Factory is 0. Setup writes 0 when either is non-zero so a Wizard PID tune cannot throw the 32-tick step past the 48-tick cage.
* Robotis resets Present to absolute-within-one-rotation when torque turns on in Position Control. Setup re-reads present after torque-on and rematches Goal if it jumped, so the horn does not yank before a certified command.
* `probe` / `open_discovering` identify only. They must not write EEPROM or enable torque. If Startup Configuration already enabled torque (DTR reboot), probe writes torque-off and does not count it as command egress. `serve` / `open` apply bench limits and torque-on. Drop torque-off runs only when this process enabled torque; identify-only close used to write `torque_enable=0` and increment egress before serve.
* Setup refuses torque-on when Present Input Voltage is outside Wizard min/max voltage EEPROM (`dxl_vin_outside_wizard_limits`). It does not widen those limits. A 0 or failed VIN read used to skip that check; setup now refuses (`dxl_vin_unreadable_before_torque`). A failed or zero voltage-limit EEPROM read used to invent factory 35/70; setup now refuses (`dxl_voltage_limits_unreadable_before_torque`). * CI `os-users` runs `scripts/metal-pty-sequence.sh` so campaign-script first-contact bugs (empty `METAL_CMD_ID`, crash-replay hang, replay latch, identify-only probe, PTY `fuser` exclusive) fail before the XL330 bench. * Linux asserts DTR on the first USB-serial open. Cheap FTDI/CP2102 boards wire that to servo RESET. A fresh USB-serial open restores kernel-default HUPCL (`serialport` `cfmakeraw` does not clear it), so a pre-open `stty -hupcl` is lost. Do not speak 1 Mbps during settle (CH340 wedge). A half-duplex adapter that needs a longer reboot than 500 ms, or a Wizard 2/3/4 Mbps bus, is still a first-contact hole.
